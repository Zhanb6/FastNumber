## 1. Назначение и цели

Система используется непосредственно во время форума для проведения нескольких публичных розыгрышей призов среди зарегистрированных посетителей.

**Сценарий в одну строку:**
QR-код → регистрация → уникальный номер → участие в live-розыгрышах, которые запускает организатор и которые транслируются на большой экран.

**Цели:**
- быстрая регистрация с телефона (≤ 10 секунд от сканирования до получения номера);
- гарантированная уникальность номеров;
- честный, проверяемый выбор победителя на сервере;
- эффектная трансляция розыгрыша на LED-экран без ручных действий на экране;
- переиспользование системы на следующих мероприятиях ZIZ INC.

## 2. Принципы разработки

**DO NOT OVERENGINEER.** Это live event software.

Приоритеты (в порядке убывания):

1. Надёжность.
2. Скорость регистрации.
3. Невозможность дублирования номера.
4. Стабильный realtime.
5. Красивый Live Draw.
6. Простая Admin Panel.

Запрещено:
- внешние API в критической логике;
- сторонняя авторизация (OAuth, SaaS-auth);
- внешние CDN (шрифты, скрипты, стили — только self-hosted);
- «enterprise»-функции без прямой пользы для события (мультитенантность, роли и права, микросервисы, очереди сообщений и т. п.).

## 4. Регистрация участника

### 4.1. Форма

| Поле | Обязательность | Состояние по умолчанию |
|---|---|---|
| Имя | Обязательное | Включено |
| Фамилия | Обязательное | Включено |
| Телефон | Опционально / обязательно (настраивается) | Выключено |
| Email | Опционально / обязательно (настраивается) | Выключено |
| Компания | Опционально / обязательно (настраивается) | Выключено |

- Дополнительные поля включаются/выключаются и помечаются обязательными через настройки (`/admin` → Настройки), без изменения кода.
- Валидация на клиенте и на сервере (Pydantic):
  - имя и фамилия: 1–60 символов после `trim`, допускаются кириллица, латиница, казахские буквы, пробел, дефис, апостроф;
  - телефон: формат E.164 после нормализации (`+7XXXXXXXXXX`);
  - email: стандартная валидация.
- Кнопка: **«Получить номер»**. Во время отправки — состояние загрузки, повторное нажатие заблокировано.
- Если регистрация закрыта (`registrationOpen = false`) — вместо формы показывается сообщение «Регистрация закрыта».

### 4.2. Экран после регистрации

Номер занимает центральную часть экрана. Никаких лишних элементов.

```
KAZAKHSTAN
TRAVEL FORUM

Вы зарегистрированы

ВАШ НОМЕР

1374

Имя Фамилия

Сохраните этот номер.
Ожидайте розыгрыша на главной сцене
```

- Branding Kazakhstan Travel Forum.
- Экран корректно отображается на ширине от 320 px.
- Опционально (низкий приоритет): кнопка «Сохранить скриншот» не требуется — достаточно подсказки «Сделайте скриншот».

### 4.3. Производительность страницы регистрации

- First Load JS страницы `/` — не более ~100 KB gzip (без Framer Motion на этой странице или с минимальным использованием).
- Шрифты — self-hosted, `font-display: swap`, subset кириллица + латиница.
- LCP на 4G ≤ 1.5 с.

## 5. Нумерация

- Первый участник получает `startNumber` (по умолчанию **1000**), далее 1001, 1002, …
- Номер присваивается **атомарно на backend** — одновременная регистрация не может выдать одинаковые номера.
- Реализация: отдельная таблица-счётчик `number_counter` с `SELECT … FOR UPDATE` в транзакции регистрации (или PostgreSQL `SEQUENCE` со стартовым значением из конфигурации) + ограничение `UNIQUE(number)` в таблице участников как вторая линия защиты.
- **Номера никогда не переиспользуются**, в том числе после удаления участника.
- Архитектура не ограничивает количество участников числом 2000. Поведение при достижении `maxNumber` задаётся настройкой:
  - `onMaxReached = "continue"` (по умолчанию) — продолжать выдачу 2001, 2002, …;
  - `onMaxReached = "close"` — закрыть регистрацию и показать сообщение.
- Минимальная целевая нагрузка: 1000+ участников, пик — 50 регистраций в секунду.

## 6. Защита от повторной регистрации

Soft protection — не должна мешать реальным посетителям (общий Wi-Fi форума, один телефон на двоих и т. п.).

1. При первой регистрации сервер генерирует `device_token` (UUID v4, криптографически случайный) и возвращает его клиенту.
2. Клиент хранит токен в `localStorage` **и** в cookie (`SameSite=Lax`, срок — 30 дней).
3. При открытии `/` клиент вызывает `GET /api/me/{token}`:
   - участник найден и активен → сразу показывается экран с номером;
   - участник удалён / токен не найден → показывается форма.
4. Повторный `POST /api/register` с уже существующим валидным `device_token` возвращает **существующую** запись (идемпотентность), а не создаёт новую.
5. Rate limit по IP — мягкий: не более 30 регистраций в минуту с одного IP (учитывать общий NAT площадки). Значение настраивается.
6. Блокировка по IP/fingerprint **не применяется**.
7. Ссылка «Это не я / зарегистрировать другого человека» внизу экрана с номером — очищает локальный токен и показывает форму (для случая одного телефона на нескольких людей).

Администратор может удалить любого участника (см. 12.3).

## 7. Розыгрыши (раунды)

### 7.1. Атрибуты розыгрыша

| Атрибут | Описание |
|---|---|
| Название | «Розыгрыш №1» |
| Приз | «Авиабилеты» |
| Описание | Свободный текст |
| Порядковый номер | Для сортировки и отображения |
| Статус | См. 7.2 |
| Запланированное время | Дата и время (информационно) |
| Время запуска / завершения | Фиксируются системой |
| Победитель | Ссылка на участника (после подтверждения) |

Пример набора:

| № | Название | Приз |
|---|---|---|
| 1 | Розыгрыш №1 | Авиабилеты |
| 2 | Розыгрыш №2 | Проживание в отеле |
| 3 | Розыгрыш №3 | Путешествие на двоих |

### 7.2. Статусы розыгрыша

```
DRAFT ──start──▶ PENDING_CONFIRMATION ──confirm──▶ COMPLETED
                      │   ▲
                      └───┘ redraw
DRAFT ──cancel──▶ CANCELLED
```

| Статус | Описание | Разрешённые действия |
|---|---|---|
| `DRAFT` | Создан, не проводился | Редактировать, удалить, запустить, отменить |
| `PENDING_CONFIRMATION` | Победитель выбран, ожидает подтверждения | Подтвердить, повторить (redraw) |
| `COMPLETED` | Победитель подтверждён | Только просмотр |
| `CANCELLED` | Отменён без проведения | Только просмотр |

- Редактирование названия/приза/описания разрешено только в статусе `DRAFT`.
- Розыгрыш в статусе `COMPLETED` изменить невозможно ни через UI, ни через API.
- Одновременно может проводиться только один розыгрыш (глобальная блокировка «активного» розыгрыша).

### 7.3. Правила участия

Eligible-участник для розыгрыша — участник, у которого одновременно:
- статус `ACTIVE` (не удалён и не дисквалифицирован);
- если `allowPreviousWinners = false` (по умолчанию): нет подтверждённой (`CONFIRMED`) победы в других розыгрышах;
- нет отклонённого (`REJECTED`) результата в **текущем** розыгрыше (тот, кого «перевыбрали», не участвует в redraw этого же раунда).

Настройка в Admin: **[x] Исключать предыдущих победителей**. Администратор может её выключить глобально; дополнительно — переопределить для конкретного розыгрыша.

## 8. Алгоритм выбора победителя

1. Победитель выбирается **только на backend**. Frontend никогда не определяет победителя.
2. Источник случайности — `secrets.SystemRandom()` / `secrets.randbelow()` (CSPRNG). `random.random()` запрещён.
3. Порядок операций при `start` (одна транзакция):
   1. блокировка строки розыгрыша (`SELECT … FOR UPDATE`), проверка статуса `DRAFT`;
   2. выборка списка eligible-участников (отсортированного по `number`);
   3. если список пуст — ошибка `409 NO_ELIGIBLE_PARTICIPANTS`;
   4. `index = secrets.randbelow(len(list))`;
   5. создание `DrawResult (status = SELECTED)`, перевод розыгрыша в `PENDING_CONFIRMATION`, запись `started_at`;
   6. запись в Audit Log с количеством eligible-участников и хешем (SHA-256) отсортированного списка их номеров — для последующей проверки честности;
   7. commit.
4. **Только после commit** отправляется realtime-событие на Live Screen и запускается анимация. Результат зафиксирован в БД до начала reveal.
5. Redraw: текущий `DrawResult` → `REJECTED` (с причиной, если указана), создаётся новый `DrawResult (SELECTED)` по тому же алгоритму, история сохраняется, в Audit Log пишется `DRAW_REDRAW`.
6. Confirm: `DrawResult` → `CONFIRMED`, `Draw.winner_id` заполняется, статус `COMPLETED`, `completed_at`.

## 9. Live Draw Screen

URL: **`/draw`**. Оптимизация под **1920×1080**, корректное масштабирование на 1280×720 и 3840×2160 (размеры через `vw/vh`/`clamp`).

### 9.1. Требования

- Fullscreen-friendly: кнопка/клавиша `F` для входа в полноэкранный режим; курсор скрывается после 3 с бездействия.
- Никаких элементов управления розыгрышем на экране — только отображение.
- Не требует авторизации, но доступен только на чтение (опционально — защита параметром `?key=` из env `DRAW_SCREEN_KEY`).
- Экран должен работать часами без перезагрузки (без утечек памяти, анимации останавливаются в состоянии покоя).
- Индикатор соединения — малозаметная точка в углу (зелёная / жёлтая «переподключение»). Для зрителей не должен отвлекать.

### 9.2. Состояния экрана

| Состояние | Что отображается |
|---|---|
| `IDLE` | `KAZAKHSTAN TRAVEL FORUM` · `РОЗЫГРЫШ` · `Участников: XXX` (обновляется в realtime) · название следующего розыгрыша и приз (если есть) · «ожидание запуска» — мягкая фоновая анимация |
| `COUNTDOWN` | Название розыгрыша и приз |
| `DRAWING` | Быстрая смена номеров с замедлением |
| `WINNER` | `ПОБЕДИТЕЛЬ` · `№ 1374` · `ИМЯ ФАМИЛИЯ` · приз · конфетти |
| `COMPLETED` | Победитель подтверждён: карточка победителя остаётся на экране до перехода в `IDLE` администратором (кнопка «Вернуть экран в режим ожидания») |

При redraw экран возвращается в `COUNTDOWN` и проигрывает анимацию заново.

### 9.3. Подключение в середине розыгрыша

Если экран открыт/переподключился во время розыгрыша, он запрашивает `GET /api/live/current`:
- если с момента запуска прошло < 8 с — анимация продолжается с правильной позиции (по `server_time` и `started_at`);
- если ≥ 8 с — сразу показывается карточка победителя без анимации.

## 10. Анимация розыгрыша

Отдельный переиспользуемый компонент `<DrawAnimation />`.

```ts
interface DrawAnimationProps {
  drawTitle: string;
  prize: string;
  winner: { number: number; firstName: string; lastName: string };
  numberPool: number[];        // номера участников для визуальной прокрутки
  startedAt: number;           // серверное время старта, ms
  serverOffsetMs: number;      // поправка часов клиента
  durationMs?: number;         // по умолчанию 8000
  onRevealComplete?: () => void;
}
```

### 10.1. Тайминг

| Время | Фаза | Состояние |
|---|---|---|
| 0–1 с | Появление названия розыгрыша и приза | `COUNTDOWN` |
| 1–5 с | Очень быстрая смена случайных номеров (~20–30 смен/с) | `DRAWING` |
| 5–7 с | Плавное замедление (ease-out), последний номер — номер победителя | `DRAWING` |
| 7–8 с | Остановка и короткая пауза, лёгкая пульсация номера | `DRAWING` |
| 8 с | Reveal: `ПОБЕДИТЕЛЬ`, номер, имя, приз, конфетти / частицы / glow | `WINNER` |

### 10.2. Требования

- Номера во время прокрутки — **только визуализация**, берутся из пула реальных номеров eligible-участников (чтобы на экране не мелькали несуществующие номера).
- Смена цифр через `requestAnimationFrame`, без ре-рендера всего дерева React на каждый кадр.
- Конфетти — собственная лёгкая реализация на `<canvas>` (или маленькая локальная зависимость), 60 FPS на среднем мини-ПК/Smart TV-браузере.
- Стиль — premium technology / travel event. **Не казино**: без барабанов, слот-машин, золотых монет, мигающих лампочек.
- Поддержка `prefers-reduced-motion` (упрощённая анимация).
- Опционально: звуковое сопровождение (tick + reveal), выключено по умолчанию, файлы локальные.

## 11. Realtime-синхронизация

### 11.1. Транспорт

- Основной: **WebSocket** `WS /ws/live` (FastAPI native).
- Heartbeat: сервер отправляет `ping` каждые 15 с; клиент переподключается при отсутствии сообщений > 30 с.
- Автопереподключение с экспоненциальной задержкой (1 → 2 → 4 → … → максимум 10 с).
- **Fallback:** при недоступности WebSocket клиент опрашивает `GET /api/live/current` каждые 2 с.
- После любого переподключения клиент запрашивает `GET /api/live/current` — источник истины всегда БД, а не последнее событие.

### 11.2. Масштабирование

Backend запускается одним процессом (достаточно для события). Если потребуется несколько воркеров — рассылка событий через PostgreSQL `LISTEN/NOTIFY` (без Redis).

### 11.3. Формат событий

```json
{
  "type": "state",
  "state": "COUNTDOWN",
  "server_time": 1789000000000,
  "draw": {
    "id": "uuid",
    "title": "Розыгрыш №1",
    "prize": "Авиабилеты",
    "started_at": 1789000000000
  },
  "winner": { "number": 1374, "first_name": "Имя", "last_name": "Фамилия" },
  "number_pool": [1000, 1001, 1002],
  "participants_count": 847
}
```

Типы событий:

| type | Когда |
|---|---|
| `state` | Смена состояния экрана (полный снимок) |
| `participants_count` | Изменение числа участников (не чаще 1 раза в 2 с, с дебаунсом) |
| `ping` | Heartbeat |

## 12. Admin Panel

URL: **`/admin`**. Desktop-first, responsive (планшет — полностью, телефон — базово).

### 12.1. Авторизация

- Логин/пароль из переменных окружения `ADMIN_LOGIN`, `ADMIN_PASSWORD`.
- При старте backend создаёт/обновляет запись `Admin` с bcrypt-хешем пароля.
- Сессия — подписанный JWT в `httpOnly`, `Secure`, `SameSite=Strict` cookie, срок 12 ч.
- Ограничение перебора: 5 неудачных попыток за 5 минут с IP → блок на 5 минут.

### 12.2. Dashboard

Карточки с крупными цифрами (обновление в realtime):
- Всего зарегистрировано
- Сегодня зарегистрировано (по часовому поясу `EVENT_TIMEZONE`, по умолчанию `Asia/Almaty`)
- Проведено розыгрышей
- Победителей

Дополнительно: ссылка «Открыть Live Screen», QR-код ссылки на регистрацию (генерируется локально, для печати), статус регистрации (открыта/закрыта) с переключателем.

### 12.3. Участники

Таблица:

| № | Имя | Фамилия | Дата регистрации | Статус | Выигрывал |
|---|---|---|---|---|---|

- Поиск по имени, фамилии, номеру (одно поле, серверный поиск, `ILIKE` + точное совпадение по номеру).
- Фильтры: статус, выигрывал/нет.
- Пагинация (50 строк на страницу), сортировка по номеру и дате.
- Действия над строкой:
  - **Дисквалифицировать** (с необязательной причиной) → статус `DISQUALIFIED`, не участвует в розыгрышах;
  - **Восстановить** → статус `ACTIVE`;
  - **Удалить** — soft delete (статус `DELETED`), с подтверждением. Номер не освобождается. Удалённые скрыты по умолчанию, видны через фильтр.
- Нельзя удалить/дисквалифицировать участника, чей результат в статусе `PENDING_CONFIRMATION` — сначала redraw или confirm.
- Кнопка **«Экспорт CSV»**.

### 12.4. Розыгрыши

- Список розыгрышей: порядок, название, приз, статус, время, победитель.
- Создание / редактирование (только `DRAFT`) / удаление (только `DRAFT` без результатов) / отмена.
- Страница конкретного розыгрыша:

```
Розыгрыш №1
Приз: Авиабилеты
Eligible участников: 847
Статус: DRAFT

        [ START DRAW ]
```

- Кнопка **START DRAW** — крупная, заметная.
- Confirmation-диалог: **«Запустить розыгрыш среди 847 участников?»** — число актуализируется запросом к серверу в момент открытия диалога.
- После подтверждения → `POST /api/admin/draws/{id}/start` → backend выбирает и сохраняет победителя → Live Screen автоматически запускает анимацию.
- Admin видит результат сразу:

```
№ 1374
Имя Фамилия

[ Подтвердить победителя ]   [ Повторить розыгрыш ]
```

- Кнопки подтверждения/повтора становятся активными через 8 с (после окончания анимации на экране), чтобы избежать случайных нажатий во время reveal.
- «Повторить розыгрыш» — с обязательным подтверждением и необязательной причиной («победитель отсутствует в зале» и т. п.).
- История результатов розыгрыша (все `SELECTED` / `REJECTED` / `CONFIRMED`) видна на странице.
- Кнопка «Вернуть экран в режим ожидания» — переводит Live Screen в `IDLE`.

### 12.5. Победители

Таблица: розыгрыш, приз, номер, имя, фамилия, дата/время подтверждения. Кнопка **«Скачать CSV»**.

### 12.6. Настройки

- Название мероприятия
- Регистрация открыта / закрыта
- Исключать предыдущих победителей
- Включение и обязательность полей: телефон, email, компания
- Поведение при достижении `maxNumber`
- Стартовый номер — **изменяется только до первой регистрации**, далее поле заблокировано

### 12.7. Audit Log

Отдельный раздел: таблица с фильтрами по типу действия, розыгрышу, участнику. Только чтение.

## 13. Audit Log

### 13.1. Логируемые действия

| action | Событие |
|---|---|
| `PARTICIPANT_REGISTERED` | Регистрация участника |
| `PARTICIPANT_DISQUALIFIED` | Дисквалификация |
| `PARTICIPANT_RESTORED` | Восстановление |
| `PARTICIPANT_DELETED` | Удаление |
| `DRAW_CREATED` / `DRAW_UPDATED` / `DRAW_DELETED` / `DRAW_CANCELLED` | Операции с розыгрышем |
| `DRAW_STARTED` | Запуск розыгрыша (кол-во eligible, хеш списка) |
| `WINNER_SELECTED` | Выбран победитель |
| `DRAW_REDRAW` | Повтор розыгрыша (отклонённый участник, причина) |
| `WINNER_CONFIRMED` | Подтверждение победителя |
| `SETTINGS_CHANGED` | Изменение настроек (старое и новое значение) |
| `ADMIN_LOGIN` / `ADMIN_LOGIN_FAILED` | Вход в админку |
| `EXPORT` | Выгрузка CSV |

### 13.2. Поля записи

`timestamp`, `action`, `participant_id`, `draw_id`, `admin_login`, `ip`, `metadata` (JSON).

### 13.3. Неизменяемость

- Audit Log — append-only. В API нет методов изменения/удаления.
- Для проведённого розыгрыша невозможно изменить результат незаметно: любые изменения проходят только через `redraw`/`confirm` и логируются; `COMPLETED` неизменяем.
- Дополнительно (рекомендуется): PostgreSQL-триггер, запрещающий `UPDATE`/`DELETE` в таблице `audit_log`.

## 19. Надёжность и Emergency Mode

- Вся критическая логика работает без интернета при наличии локальной сети (ни одного внешнего запроса в runtime).
- Все контейнеры — `restart: unless-stopped`, healthchecks для `db`, `backend`, `frontend`.
- Данные PostgreSQL — в именованном volume.
- Резервное копирование: сервис/скрипт `pg_dump` раз в 15 минут в папку `./backups` (с ротацией).
- Admin может:
  - экспортировать всех участников в CSV;
  - скачать список победителей;
  - провести розыгрыш **непосредственно на сервере** через CLI:

```bash
docker compose exec backend python -m scripts.draw_cli list
docker compose exec backend python -m scripts.draw_cli start <draw_id>
docker compose exec backend python -m scripts.draw_cli redraw <draw_id> --reason "..."
docker compose exec backend python -m scripts.draw_cli confirm <draw_id>
```

  CLI использует те же сервисы, что и API (один код выбора победителя), пишет в Audit Log (`admin_login = "cli"`) и отправляет события на Live Screen.
- Если Live Screen потерял соединение — после переподключения он восстанавливает актуальное состояние из БД.
- Регистрация и розыгрыш не зависят друг от друга: запуск розыгрыша не блокирует регистрацию (и наоборот, кроме короткой транзакционной блокировки).

## 20. Безопасность

- Все секреты — только через env; `.env` в `.gitignore`.
- Пароль администратора хранится только в виде bcrypt-хеша.
- CSRF: `SameSite=Strict` cookie + проверка заголовка `Origin` для изменяющих запросов.
- Защита от SQL-инъекций — только параметризованные запросы через ORM.
- Экранирование пользовательских данных в UI (React по умолчанию) и в CSV (защита от CSV-инъекций: префикс `'` для значений, начинающихся с `= + - @`).
- Security headers в nginx: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, базовый CSP.
- HTTPS — через внешний reverse proxy/хостинг или опциональный Caddy/certbot (описать в README).
- Персональные данные: хранить минимум полей; в README — инструкция по удалению данных после мероприятия.

## 23. Критерии приёмки

### Регистрация и нумерация

1. Первый зарегистрированный участник получает номер 1000, далее последовательно.
2. Нагрузочный тест: 500 параллельных регистраций → 500 уникальных номеров, без пропусков и дублей.
3. Повторное открытие `/` с того же устройства показывает существующий номер, новая запись не создаётся.
4. Удалённый участник при повторном открытии видит форму; его номер повторно не выдаётся.
5. При `registrationOpen = false` регистрация невозможна ни через UI, ни через API.

### Розыгрыш

6. Победитель выбирается только из eligible-участников; дисквалифицированные и удалённые не участвуют.
7. При включённой настройке подтверждённые победители не участвуют в следующих розыгрышах; при выключенной — участвуют.
8. Результат сохраняется в БД до отправки события на Live Screen.
9. Redraw сохраняет предыдущий результат со статусом `REJECTED` и не выбирает того же участника в этом раунде.
10. Повторное нажатие START DRAW / двойной запрос не создаёт второй результат.
11. `COMPLETED`-розыгрыш невозможно изменить через API.
12. При отсутствии eligible-участников показывается понятная ошибка.

### Live Screen

13. После нажатия START DRAW анимация на Live Screen запускается в течение 1 с без ручных действий.
14. Длительность анимации 8 с ± 0,5 с, тайминг соответствует разделу 10.
15. После перезагрузки страницы `/draw` в любом состоянии отображается актуальное состояние.
16. После кратковременного отключения сети экран автоматически переподключается.
17. Экран корректен на 1920×1080, без скроллов, в fullscreen.

### Admin и аудит

18. Все действия из раздела 13.1 фиксируются в Audit Log с timestamp, action, participant, draw, admin.
19. CSV корректно открывается в Excel с кириллицей.
20. Розыгрыш можно провести через CLI с тем же результатом в БД и на Live Screen.

### Производительность и автономность

21. Страница регистрации: Lighthouse Performance (mobile) ≥ 90.
22. В runtime нет ни одного запроса к внешним доменам (проверка DevTools → Network на всех трёх экранах).
23. Система запускается командой `docker compose up -d` на чистой машине с Docker.
